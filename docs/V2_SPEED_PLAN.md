# H3 Studio v2 — 生成時間の徹底調査と改善提案

作成: 2026-09-07 / 対象: 長尺 Motion Trace（18秒）が46分かかる問題

**この文書は提案であって、既定値の変更ではない。** 採用は A/B の後（CLAUDE.md
「未検証の値を既定にしない」）。

---

## 1. 時間はどこに消えているか（自前の実測）

18秒 / 430フレーム / 0.4MP (480×864) / 12 steps / RTX 6000 Ada 48GB、
2026-09-07 の実行をライブログから取得:

```
2/12 [06:47<33:59, 203.98s/it]
...
9/12 [30:34<10:11, 203.80s/it]
```

**203.8 秒/step、12本すべてで ±0.25秒**。前日の別Podでの 213 秒/step ともほぼ一致する。

| 工程 | 時間 | 割合 |
|---|---|---|
| **サンプリング** | 203.8 × 12 = **2446 秒** | **約 88%** |
| Qwen3-VL エンコード（MISS時） | 約 75〜90 秒 | 約 3% |
| VAE デコード + 保存 + その他 | 約 240 秒 | 約 9% |
| 合計 | 約 2780 秒（46分） | 100% |

### 1.1 フレーム数に対して超線形（指数 1.81）

| | フレーム | 時間 |
|---|---|---|
| 2秒 | 56 | 約 70 秒 |
| 18秒 | 430 | 2778 秒 |
| 比 | **7.68倍** | **39.7倍** |

`log(39.7) / log(7.68) = **1.81**`。ほぼ二乗で、動画トークン長に対する
attention のコストがそのまま出ている。

### 1.2 ここから決まる、効く場所と効かない場所

- **効く**: サンプリング（88%）を削るもの — 分割・steps・解像度・step キャッシュ・sparse attention
- **ほぼ効かない**: エンコードを削るもの（3%）

> **重要な含意:** コミュニティが最も語っている手法（conditioning / latent の
> ディスクキャッシュ、「950秒 → 96秒」）は**私たちが既に持っている**（CLIPCached）。
> しかしそれが効くのは**エンコードが全体の半分を占める短尺**の話であり、
> 18秒では全体の3%にしか触れない。**彼らのベンチと私たちの支配項は違う。**

## 2. 候補の全数調査

「実在」はこの環境（ComfyUI v0.34.2 `169fcf35` / RTX 6000 Ada SM89 / CUDA 13.0 /
torch 2.14.0）に対する実確認。

| # | 手法 | 攻撃する対象 | この環境での実在 | 実測の裏付け | Ref2VA での実測 | リスク |
|---|---|---|---|---|---|---|
| A | **分割（6秒×3）** | 超線形性そのもの | 追加なしで可能 | **自前実測**（指数1.81）＋ [matsuo-koya] の運用（28分割MV 3.8h→2.7h） | — | 継ぎ目のドリフト |
| B | **steps 12→8** | サンプリング（線形） | 可能（`quality_overrides`） | 203.8秒/step 実測 | — | 12は既に推奨下限未満 |
| C | **解像度 0.4→0.25MP** | サンプリング（超線形） | 可能（`quality_overrides`） | 2秒A/Bから外挿 | — | 480p時点で既に甘い |
| D | **EasyCache** | サンプリング（step再利用） | **`EasyCache` 実在**（ネイティブ） | 他者 1.81倍。ただし既定は破綻あり | なし | 高周波の劣化 |
| E | **DualRes 二段解像度** | サンプリング | **`MiniMaxH3CLIPCachedRef2VADualRes` 実在**（CLIPCached同梱） | なし（同発想の別実装は10秒0.5MPで27〜35%） | なし | グラフ変更 |
| F | **H3-Optimizations**（sparse attention） | サンプリング（attention 本体） | 未導入。**要件は全て充足** | **5秒1.51倍 / 10秒1.93倍** | なし | 計算が変わる。baseline除外系統 |
| G | SPEED パック（多段解像度） | サンプリング | 未導入 | 10秒0.5MP で 833→540秒 | なし | **Euler専用** / **非商用ライセンス** |
| H | FastVideo VSA | attention | 未導入 | — | なし | **B200級が必要**との報告 |
| I | SageAttention | attention | 未導入（パッケージ無し） | 1.37倍 | なし | **長尺でノイズ報告**（185,640トークン） |
| J | Turbo LoRA（Ref2VA） | steps | **4step v0.1 のみ・Pod未配置** | fl2vaは1.87〜2.2倍 | なし | 手の破綻報告 |
| K | `TorchCompileModel` | コンパイル | 実在 | 他者は常時バイパス運用 | なし | 初回コンパイル時間 |

### 2.1 F（H3-Optimizations）の要件照合 — 全て満たしている

| 要件 | この環境 |
|---|---|
| ComfyUI 0.33.0 以上 | **0.34.2** ✅（固定バージョンを変えずに済む） |
| NVIDIA SM75 以上 | RTX 6000 Ada = **SM89** ✅（`FROST BF16` は SM89 専用＝ちょうど該当） |
| Python 3.10+ | ✅ |
| glibc 2.34+ | Ubuntu 24.04 ✅ |
| 追加 Python パッケージ | 既定の Native Kitchen INT8 では**不要** |

**長尺ほど効くと明記された唯一のパッケージ**（5秒1.51倍 → 10秒1.93倍）で、
指数1.81という私たちの実測と原因が一致している。

作者の警告をそのまま引く: sparse attention はモデルの計算を変える。無損失を
保証できる attention 率は存在せず、H3 は特に**サンプリング初期の削減に敏感**。

### 2.2 他者が「効かなかった」と記録しているもの

- **VAE デコード最適化** — 速くならず（13.0→12.2秒）**絵が壊れる**
- **Alibaba-pai Acc-LoRA** — LoRA ではなく PDD 重み。対応サンプラーが ComfyUI に無い
- **Sage / VSA** — nvcc が必要、VSA は専用カーネル＋B200

私たちの 9% を占める VAE デコードは、**触らない**方が良いと既に分かっている。

## 3. 提案（3フェーズ）

### Phase 0 — GPU 不要・今日からできる

**0-1. 分割ワークフロー（最優先）**
Studio は参照動画の**冒頭フレームしか使わない**（`frames[:frame_count]`）ので、
2本目以降には元動画を切り出したものを渡す必要がある。Mac 側の ffmpeg で切るだけ。

推定（指数1.81・実測 203.8秒/step を基準）:

| 作り方 | サンプリング/step | 1本あたり | 合計 | 対 18秒×1 |
|---|---|---|---|---|
| 18秒 × 1 | 203.8 s | 46 分 | **46 分** | 1.00 |
| 9秒 × 2 | 58.2 s | 12.5 分 | **25 分** | 1.8倍速 |
| **6秒 × 3** | 27.1 s | 6.5 分 | **19.5 分** | **2.4倍速** |
| 6秒×3 + 8steps | 27.1 s | 4.6 分 | **14 分** | 3.3倍速 |

**副次効果:** 6秒 = 141フレームは H3 の学習範囲（124〜362）の**中**。
現在の 430フレームは範囲外（ノード定義の tooltip で確認）。

**やること:** `scripts/split_source_video.sh`（ffmpeg で N 秒ずつ切る）と、
Studio 側に「分割して投入」導線。UI に `steps` / `megapixels` を出す（API は既に対応済み）。

**0-2. 既定値は変えない。** Draft の steps を下げるかは A/B の後。

### Phase 1 — GPU 1セッション（インストール不要・約30分）

D（EasyCache）と E（DualRes）を測る。**どちらも既に入っているノード**なので
venv を触らない = baseline リスクが最小。

| 条件 | 変数 | 期待 |
|---|---|---|
| 基準 | 6秒 / 0.4MP / 12step | 6.5 分 |
| D1 | + EasyCache `end_percent=0.70` | 約1.25倍速・破綻なし |
| D2 | + EasyCache 既定 `0.95` | 約1.8倍速・**破綻が出るはず**（出れば他者報告の再現） |
| E1 | DualRes 二段 | 未知 |

**判定基準（事前に決める）:** 顔・髪・生地の高周波が Draft の判断に耐えるか。
D2 で破綻が出なければ、他者の報告がこのカードでは当てはまらないと分かるのでそれも収穫。

### Phase 2 — GPU 1セッション（venv 変更あり・約40分）

F（H3-Optimizations）。**`scripts/venv_snapshot.sh` → `install_experiment.sh` →
A/B → 不採用なら `venv_rollback.sh`** の既存機構に乗せる。

| 条件 | 期待 |
|---|---|
| 基準（6秒） | 6.5 分 |
| F1 attention 予算 50%（Denser Early） | 1.3〜1.5倍速 |
| F2 attention 予算 30% | 1.5〜1.9倍速・劣化リスク大 |
| F3 18秒で F1 | **長尺ほど効くかの確認**（ここが本命） |

**Ref2VA での測定は誰もしていない。** F3 は世界で初めて測る値になる。

### 積み上げの見込み（すべて推定）

| 段階 | 18秒相当の合計時間 |
|---|---|
| 現状 | 46 分 |
| + 分割（6秒×3） | 19.5 分 |
| + EasyCache 安全設定 | 約 15 分 |
| + sparse attention（F1が効けば） | 約 10〜11 分 |
| + 8 steps | 約 7〜8 分 |

**4〜6倍速が射程。** ただし各段の劣化は積み上がるので、Final には効かせない
（「速度より Final 品質」の原則）。

## 4. やらないこと

| | 理由 |
|---|---|
| G（SPEED パック） | **Euler 専用** — baseline が通したのは `res_multistep`。加えて**非商用ライセンス**。同じ発想の E が手元にあり、制約が無い |
| H（FastVideo VSA） | B200 級が必要との報告。RTX 6000 Ada では期待薄 |
| I（SageAttention） | 未導入 + **長尺でノイズ**の報告。私たちの用途は長尺 |
| J（Ref2VA Turbo） | 4step v0.1 しか無く、手の破綻が既知 |
| VAE デコード最適化 | 他者が「速くならず絵が壊れる」と実測済み |
| ComfyUI のバージョン更新 | 禁止事項 |

## 5. 判定と記録のルール

- 各フェーズは `scripts/ab_test.sh`（nonce・ゲート・動画回収つき）で測る
- **1条件1変数**。cache HIT/MISS は ComfyUI ログの ground truth を採る
- 結果は `docs/V2_AB_TESTS.md` と `results/VALIDATION_LOG.md` に実測値で書く
- **勝った値だけ** `studio/graph.py` の `PRESETS` に入れる。Draft と Final は別に判断する
- baseline（`results/V2_READY` / BASELINE_READY / 固定ワークフロー）には触れない
